# Camera Deck Slate — реализация и проверка

Дата отчёта: 21 октября 2026. Выпуск: **Slate 0.9.0, code 13**. Основание: подтверждённое пользователем ТЗ `Camera_Deck_Glide_Professional_Overhaul_Prompt.md`.

Это отчёт о работающих изменениях в проекте. Выпуск остаётся экспериментальным: эмулятор и автоматические проверки не подтверждают работу всех физических Android-камер.

## Что изменено

### Windows

- Основной интерфейс разделён на четыре рабочих пространства с реальными функциями: мониторинг, управление выбранной камерой, продакшн и материалы.
- Настройки вынесены из каждой видеокарточки в инспектор. В карточке остались изображение, состояние, быстрый спуск/запись, разворачивание и отключение.
- Применена общая графитовая палитра, компактные компоненты, ограниченный жёлтый акцент, красный цвет записи и собственные векторные иконки. Основной монитор использует чёрные поля вместо увеличенной размытой копии изображения; размытие сохранено в диалогах.
- Сохраняются геометрия окна, количество колонок, выбранная идентичность камеры и группы. Выбор не сбрасывается при обновлении статуса.
- Список устройств включает телефоны, подключённые вручную по IP, и показывает состояние подключения/записи.
- Фото и видео имеют соответствующие действия и отдельные настройки. Инспектор показывает измеренные ISO/выдержку, состояние микрофона и подтверждение создания аудиодорожки.
- Групповые старт/стоп проверяют готовность каждой камеры, ожидают подтверждённого состояния и показывают индивидуальные результаты. Ошибка одной камеры не останавливает успешно запущенные. Неподтверждённый старт автоматически повторно не отправляется.
- Есть временной журнал операций и оценка отношения монотонных часов телефона/ПК с сетевой неопределённостью. Это не покадровая синхронизация.
- Медиабраузер получает реальные миниатюры, размеры и длительность. Есть поиск, фильтры, страницы, прогресс скачивания, повтор, воспроизведение загруженного видео и открытие фото. Отсутствующая миниатюра не скрывает метаданные или материал.
- Незавершённые файлы показываются отдельно и не выдаются за готовые. Для незавершённых записей ПК есть восстановление читаемых фрагментов в новый файл.
- Ошибки операций имеют понятное объяснение, последствия и действие; технические подробности раскрываются отдельно. Диагностика Windows записывается в ограниченный журнал `%LOCALAPPDATA%/CameraDeck/logs/desktop.log`, с маскированием токенов/идентичностей.

### Android

- Общие цветовые роли и оформление выделены в `CameraDesign`. Добавлены собственная круглая кнопка спуска, компактные поверхности и менее заметные второстепенные действия.
- Сохранены вертикальная/горизонтальная компоновки, добавлен чистый видоискатель с сокрытием второстепенных органов управления. Основной спуск остаётся доступным.
- Отображается длительность подтверждённой записи. Касание выбирает область AF; pinch управляет ручным зумом и отключает автозум.
- Добавлены сетка третей и безопасная область 90%.
- Показаны достоверно сообщаемые системой тепловые ограничения. Число градусов температуры сенсора не выдумывается.
- Разделены желаемый звук, захват микрофона, измеренный уровень и фактическое появление аудиодорожки записи. В API добавлены измеренные значения зума/дистанции фокусировки, если их сообщает Camera2.
- При попытке выключить работающую камеру во время записи предлагается сначала завершить запись.
- Ошибки камеры в основном статусе получили понятное описание; по нажатию доступны подробности. Исключения сохраняются в Android logcat.

## Переработка локального предпросмотра

Исходный Glide обслуживал запасной JPEG-показ таймером 100 мс и декодировал/поворачивал изображение в UI. Это ограничивало частоту показа примерно десятью обновлениями в секунду и создавало лишний JPEG-конвейер.

Теперь CameraEngine отдаёт локальному просмотру исходный NV21 из аналитического выхода. Преобразование выполняется в `LocalPreview` на выделенном потоке. Хранится один свежий вход и один результат для UI; устаревшие входы заменяются. В UI нет декодирования JPEG и создания отдельной повёрнутой копии: используется матрица отображения.

Размер преобразования ограничен 640×480 с сохранением пропорций целочисленным уменьшением. Это относится только к совместимому локальному монитору; разрешение/битрейт оригинала и профиль H.264 для Windows не меняются. Основной TextureView продолжает работать напрямую, где камера поддерживает его конфигурацию.

Дополнительно исправлена кадровая политика. Старый ограничитель «не раньше чем через 1/24 с после прошлого принятого кадра» на входе 30 FPS принимал почти каждый второй кадр. `PreviewCadence` сохраняет дробную временную сетку и даёт целевые 24, а не около 15 FPS. Это проверяется отдельным JVM-тестом.

При фоновой записи анализ лица для автозума/фокуса продолжает работать, если доступен YUV-выход. В режиме только записи без YUV такая возможность недоступна и не обещается.

## Оригинальная запись непосредственно на ПК

Это реализованная передача пакетов записывающего кодера, а не сохранение H.264/JPEG-предпросмотра и не скачивание готового файла после съёмки.

Порядок работы:

1. Телефон готов в режиме Видео; пользователь выбирает разрешение/FPS/звук.
2. Windows открывает авторизованный `/recording` и получает подтверждение версии протокола.
3. Команда запускает обычный записывающий кодер. Его конфигурация и исходные видеопакеты/AAC дублируются в `RecordingRelay`.
4. Windows создаёт дорожки по конфигурации и мультиплексирует пакеты PyAV/FFmpeg без декодирования и повторного кодирования.
5. Остановка выполняется обычной командой остановки камеры. Успех файла ПК объявляется после терминального подтверждения и успешного закрытия мультиплексора.

Поддерживаются AVC/HEVC и AAC-LC 48 кГц mono в рамках текущего записывающего конвейера. Android 10+ требуется для отключения B-кадров. Если кодер всё же выдаёт переставленные кадры, удалённая копия завершается с ошибкой вместо создания вымышленных DTS. Локальная запись Android 9 сохраняется.

**Резервная запись на телефоне обязательна в Slate.** Поэтому место на телефоне или выбранном им накопителе продолжает расходоваться. Режим «только ПК, вообще без локального файла» не реализован.

Очередь отправителя ограничена 64 МБ, пакет — 8 МБ. Сеть не блокирует записывающий кодер: при переполнении прекращается удалённая копия с явной ошибкой, а резервная запись продолжается. Windows проверяет свободное место до начала и периодически во время записи.

ПК использует фрагментированный MP4, журнал `.recording.json` и имя `.partial.mp4` до подтверждённого завершения. Инициализация MP4 отложена до первого фрагмента (`delay_moov`), чтобы сохранить начальное смещение звука/видео. При прерывании можно перепаковать читаемые фрагменты в новый MP4. Исходник не перезаписывается. Восстановление до появления первого читаемого фрагмента и после произвольного повреждения носителя не гарантируется.

Завершение окна во время удалённой записи предупреждает о прерывании копии ПК. Оно не отправляет скрытую команду остановки резервной записи на телефоне.

## Инструменты мониторинга

На Windows реализованы гистограмма, waveform, zebra с порогом яркости 235/255, приблизительный false color, сетка третей и безопасная область 90%.

Анализ выполняется вне GUI, максимум примерно четыре раза в секунду по 160×90 отсчётам. Он не создаёт неограниченную очередь и не обрабатывает скрытый видеопоток непрерывно. На изображении указано, что анализируется 8-битный предпросмотр.

Это не RAW-анализ, не калиброванный IRE, не проверка HDR и не подтверждение точного глазного AF. Peaking, вектороскоп и фирменные инструменты производителя не выдаются за реализованные.

## Совместимость и безопасность

- Android package `.aurora`, сертификат APK, публичные ключи и продукт канала `camera-deck-aurora` сохранены.
- TLS, полный pinning сертификата перед отправкой секретов, PIN, токены, DPAPI, доверенные клиенты и отзыв доступа сохранены.
- Видеопредпросмотр по прежнему протоколу остаётся совместимым; новые поля состояния являются дополнением.
- Добавлены авторизованные `/recording`, `/clock`, `/media_info`, `/thumbnail` и opt-in пагинация/показ partial-файлов.
- Обычный старый `/media` сохраняет список готовых файлов. Незавершённые файлы не навязываются старым клиентам.
- На старом телефоне Windows сохраняет текстовый каталог при отсутствии миниатюр/метаданных. Запись на ПК включается только при объявленной возможности.
- Пути материалов проверяются по разрешённой форме имени; доступ к SAF идёт через выбранное дерево документов. Новые маршруты не обходят Bearer-авторизацию.
- Подписанные обновления EXE/APK/Portable остаются на существующих идентичностях. Активная/неопределённая запись препятствует автоматической замене Windows.

## Новые и изменённые модули

Windows: `studio.py` (рабочие пространства/инспектор), `production.py` (подтверждённые групповые операции/часы), `media_browser.py` (каталог/загрузка/проигрыватель/восстановление), `recording.py` (протокол оригинала/MP4), `monitor_tools.py` (ограниченный анализ), `icons.py` (собственные SVG), `errors.py` (объяснения/журнал), а также `main.py`, `appearance.py`, `protocol.py`, `updates.py`.

Android: `CameraDesign`, `CameraIssue`, `LocalPreview`, `Nv21`, `PreviewCadence`, `RecordingRelay`, `MediaCatalog`; изменения в `CameraEngine`, `CameraService`, `MainActivity`, `AvRecorder`, `AudioEngine`, `CaptureStore`, `TrackingOverlay` и конфигурации версии.

Тесты: добавлены проверки исходного AVC/AAC без перекодирования, начального A/V-смещения, восстановления файла, границ протокола, кадровой политики, NV21, очереди/финализации relay, групповых отказов/повторов, оценки часов, инструментов яркости и рабочих пространств/каталога.

## Проверка и измерения

Проверки проводились на Windows и эмуляторе Android API 35. Сцена эмулятора синтетическая; результаты не характеризуют производительность конкретного физического телефона.

- Python: 77 тестов прошли при наличии JDK для проверки политики питания. Без JDK один такой тест пропускается явно.
- Android: сборка APK, JVM-тесты и lint. Итоговые команды/результаты записываются в CI и локальные отчёты сборки.
- Windows: исходный GUI показал реальный H.264 телефона, все четыре рабочих пространства, сохранённый выбор и отдельный полноэкранный монитор. В каталоге получены реальные миниатюры и метаданные записей эмулятора.
- Оригинальная запись: в одном из прогонов 176 видеопакетов и 278 AAC-пакетов на ПК имели тот же хеш содержимого, что и в резервном MP4 телефона. В других прогонах проверка повторена с иным числом пакетов. Обе дорожки дополнительно декодированы.
- Начальное A/V-смещение после исправления MP4: в одном прогоне 55.759 мс на ПК и 55.792 мс в файле телефона. Разница около 0.033 мс относится к сохранению временных меток/квантованию контейнера, а не к измерению физической синхронности камеры и микрофона.
- Первый вариант нового локального преобразования: примерно 10.4–11.7 FPS, 78–105 мс на преобразование. После ограничения рабочего размера: примерно 14.5–14.8 FPS, около 20 мс. После исправления дробной кадровой политики: примерно 23.6–24.3 FPS, 20–26 мс преобразования, 20–27 мс от получения локального буфера до передачи в UI.
- Старый Glide отдельным контролируемым A/B-бенчмарком не измерялся. Его исходный таймер 100 мс задавал теоретический предел локального JPEG-показа около 10 FPS.
- Принудительный разрыв только сокета записи ПК: телефон продолжил съёмку, журнал получил состояние interrupted, partial остался. Восстановленная копия содержала 45 читаемых кадров; повторная проверка также прошла.
- В одном дополнительном прогоне наблюдался незапланированный обрыв HTTP-потока. Точная причина не установлена. Три последующих полных повтора прошли. Поэтому стабильность реальной сети и длительной записи не объявляется доказанной; резерв и восстановление остаются обязательной частью сценария.

FPS здесь измерен по обновлениям отображения, а не выведен из интервала таймера. Время передачи локального буфера в UI не является sensor-to-photon задержкой, задержкой Wi-Fi или замером дисплея.

## Реализовано частично и не реализовано

- Общая система основных экранов и компонентов внедрена; часть вспомогательных диалогов Android остаётся платформенной. Это не реализация оптического Apple Liquid Glass.
- Группы имеют подтверждённые операции и временной журнал, но не синхронизируют экспозиции и не обеспечивают genlock/timecode.
- Запись на ПК работает с резервом на телефоне. PC-only без резерва не включён.
- Метаданные/миниатюры зависят от декодеров и доступности накопителя. Анализ материалов откладывается/отклоняется во время активной съёмки, чтобы не конкурировать с кодером.
- Для старого телефона без новой пагинации остаётся его прежний объём каталога. Для новых телефонов реализованы страницы.
- Часть точных возможностей зависит от производителя: 4K60, RAW и физические модули нельзя гарантировать всем телефонам.
- High-speed/maximum-sensor съёмка, фирменные HDR/Log/10-bit, iOS, USB-видеотранспорт, WebRTC/SRT/NDI, виртуальная веб-камера и аппаратное декодирование Windows не добавлены.
- Мониторный PCM-звук по-прежнему отдельный от видеопредпросмотра и не обещает lip-sync. Это не относится к сохранению общих временных меток оригинальной записи.

## Что требует физических устройств

1. Длительная запись реальных доступных режимов, включая 4K60, с нагревом и ограничениями прошивки.
2. Разные Camera2 hardware levels, реальные фронтальные/задние/физические модули, RAW и сочетания выходов.
3. Физическая ориентация телефона, pinch/touch и чистый вид в портретной/альбомной съёмке, в том числе во время записи.
4. Измерение sensor-to-photon и A/V синхронности с физическим световым/звуковым событием.
5. Несколько реальных телефонов на одном Wi-Fi, слабый сигнал, потери, смена сети и длительные повторные подключения.
6. Внешние накопители: скорость, нехватка места, отключение во время записи и поведение конкретного SAF-провайдера.
7. Windows-компьютеры без среды разработки, разные GPU/драйверы, DPI и устройства звука; установка обоих типов обновлений на предыдущую опубликованную версию.

Эти испытания не заменены предположениями и не отмечены выполненными.

## Сборка и использование

Windows: Python 3.13, зависимости из `desktop/requirements.txt`, затем `python scripts/collect_licenses.py`, `python -m pytest tests -q`, `python scripts/build_windows.py`. EXE и Portable принимают `--self-test ABSOLUTE_OUTPUT_DIRECTORY`.

Android: JDK17, Gradle8.7, SDK35/build-tools35. Из `android`: `gradle --no-daemon -PcameraDeckPreview=true :app:assembleDebug :app:testDebugUnitTest :app:lintDebug`. Опубликованный APK подписывается прежним ключом `.aurora`; тестовая подпись CI его не заменяет.

Для записи на ПК: обновить обе программы, включить камеру, выбрать Видео и поддерживаемый режим, затем «Камера → Запись оригинала на ПК». После завершения дождаться сообщения о готовом файле. При прерывании проверить резерв на телефоне и воспользоваться восстановлением в «Материалах».

Референс организации мониторинга и вынесенного управления: [официальный Sony Monitor & Control](https://creatorscloud.sony.net/catalog/en-us/monitorcontrol/index.html). Чужие иконки, изображения и исходники в продукт не переносились. Для поведения MP4 использовалась [документация FFmpeg](https://ffmpeg.org/ffmpeg-formats.html), для remux — [PyAV](https://pyav.basswood.io/docs/stable/api/container.html) и установленный исходный код библиотеки.
